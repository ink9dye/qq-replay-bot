# 前200 口径：名次来源与定时刷新（2026-11-07）

## 1. 背景：前200 实际等于前100

页面「我方 前200 / 对手 前200」显示的对局数与前100 完全一致（同一时刻 667 vs 667）。
原因不是前端，而是 `statistics_rank_scope.filter_rows` 判定前200 时只认两处名次：

- `stat_current_top100`（官方前100，固定 100 行）；
- `ranks_for()` 现查回来、存在**进程内 120 秒**的 `_CACHE`。

库里有 2125 名非前100 玩家、约 2125 个候选，`ranks_for` 只有 4 线程、每次请求最多排队 32 个、
只等 1 秒、120 秒内不重试——结构上永远补不齐（实测每请求只补回约 30 个）。
`accept()` 把「查不到名次」一律当作「不在前200」（`value is not None and 0<value<=200`），
于是前200 静默退化成前100，页面标题仍显示前200。

## 2. 改动

| 文件 | 改动 |
|---|---|
| `bot/statistics_rank_scope.py` | `filter_rows` 先读磁盘名次快照喂 `_CACHE`，只有真缺的才进官方接口队列；新查到的写回。读取一律用实际时钟，不看可能过期的查询 `now`。 |
| `bot/statistics_rank_cache.py` | `load()` 容忍 +1 小时的「未来」时间戳（迟到的请求不再把整份缓存判成过期）；新增 `FUTURE_SKEW`。 |
| `bot/statistics_cards_report.js` / `.css` / `.html` | `rank_scope.complete === false` 时在结果页明示「X 名玩家名次未知，前200 偏小」；静态资源版本号 bump 到 `20261107rank200`。 |
| `tools/backfill_rank_cache.py` | 名次回填/刷新工具：读主库玩家 → 增量或整轮查官方 → 原子写快照 + 共享缓存。 |
| `deploy/ygo-rank-refresh.{service,timer}` | 每小时以 `ygo` 身份跑一次刷新（增量）；快照超 20 小时整轮。 |

### 名次的两个来源

1. `data/rank-scope-index.json`（**快照**）：只由 `tools/backfill_rank_cache.py` 写，原子替换；
   前200 的主要依据，不会被其它进程改写。
2. `data/statistics-rank-cache.json`（**共享缓存**）：dashboard / 卡组命名 / 采集也在写；
   迟到请求可能整份改写它，所以只当兜底，坏了不影响前200。

快照超过 7 天自动失效（`_stored_ranks` 里判断），避免定时器停摆后一直用旧名次冒充。

## 4.5 2026-11-07 22:20 追加修复

上线后页面出现「名次未补齐：4 名玩家名次未知，另有 4 名查询中」，查下来是三个小问题：

1. **内存缓存过期条目被跳过**（主因）：喂缓存时写的是 `if name not in _CACHE`，两分钟后再来的请求跳过已成过期的条目，
   紧接着 `ranks_for` 把它们按 120 秒清掉 → 该轮几乎全部判为未知，于是**每隔约 2 分钟出现一次“1928 人未知”**。
   改为：已存在但过期的条目也刷新时间戳（`wall-current[1]>=120` 就重写）。
2. **告警太吵**：4 名掉榜/新玩家也弹「对局数与胜率会偏小」。现在只在 `unknown>=50` 或占候选 ≥5% 时才提示，
   属于正常抖动的几十人不再打扰。
3. **定时器 6 小时 → 1 小时**：增量只补缺的（几十个请求，秒级），掉榜/新玩家的缺口不会累积到上百。

部署：`statistics_rank_scope.py a24d1b87`（`ygo-web` 22:19 重启）、`statistics_cards_report.js c0134620`（版本号 `20261107rank200c`）。

## 5. 运维

```bash
systemctl list-timers ygo-rank-refresh.timer --no-pager      # 下次运行
journalctl -u ygo-rank-refresh -n 20 --no-pager              # full=True/False、todo 数
sudo -u ygo /usr/bin/python3 /opt/ygobot/tools/backfill_rank_cache.py --root /opt/ygobot --dry-run
```

手工整轮刷新（约 4–5 分钟）：

```bash
sudo -u ygo /usr/bin/python3 /opt/ygobot/tools/backfill_rank_cache.py --root /opt/ygobot --max-age-hours 0
```

**必须以 `ygo` 身份运行**：快照权限 600，root 写的文件服务进程读不到（本轮踩过一次）。

## 6. 回滚

1. `systemctl disable --now ygo-rank-refresh.timer`（停自动刷新）；
2. 代码回 `git revert 71c77bb 4b7fa04`，或用 `.bak-20261107-rank200` 覆盖后重启 `ygo-web`；
3. 快照/共享缓存可留可删；删了前200 会回到「只认共享缓存」的旧行为。

## 7. 未做 / 已知限制

- `collector`、`ygo-qq` 仍是旧进程，会继续改写共享缓存（不影响前200）；等它们自然重启后彻底一致。
- 快照里所有人共用同一个 `saved_at`，所以刷新是「一天一次整轮 + 其余补新」，不是逐人滚动；
  要更细的粒度需要把 `players` 值改成 `[rank, checked_at]`，当前没必要。
- 前200 口径依赖官方 `arena/user` 接口可用；接口长期不可用时快照会在 7 天后失效并回退。
